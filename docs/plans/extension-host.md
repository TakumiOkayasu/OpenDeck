## 1. 現在地と最初の到達点

[基本設計の最初のユースケース](../design/extensions.md#最初のユースケース提案)を実装対象の候補とする。
初回は、信頼済みの外部拡張の一つのパッケージが提供する複数の単発操作について、
選択・設定・別々のボタンへの割り当て・実行・終了までを一巡させる。
拡張を増やすたびにCLIや設定処理へ分岐を追加する必要がないことを確認する。

現行の根拠:

- [公開契約](../../src/opendeck/ports.py)にActionと入力能力がある。
- [設定処理](../../src/opendeck/config.py)はbuilder表を受け、操作定義ごとに一度構成する。
- [既存テスト](../../tests/test_extensions.py)が独自操作と設定・配送の接続を確認している。
- [CLI](../../src/opendeck/cli.py)はlaunchだけを登録し、入力元の寿命を所有している。
- [nativeの配送](../../native/src/runtime.cpp)はActionを直列実行し、返却結果と例外を区別する。

単発操作について不足するのは、新しい仮想キーやActionの体系ではなく、
外部の提供能力を接続する入口と、その稼働期間を所有する組み立てである。

[パッケージと機能の割り当て](../requirements/extensions.md#パッケージと機能の割り当て)は今回確認した要求である。
複数操作の提供と割り当ては初回の受入へ含める。
回転と押下の利用要求は[回転入力の要件](../requirements/rotation.md)に従い、
その入力契約の設計をホストの初回実装と分ける。
初回経路の完成を、この要求も含めた拡張利用全体の完成とは扱わない。

## 2. 契約から方式を選ぶ

言語非依存の契約と正常・失敗系の追跡は
[最小の協調と契約](../design/extensions.md#最小の協調と契約提案)を正本とする。
以下の具体方式から契約を逆算しない。

### 推奨する初回方式

**OpenDeckと同じPython環境へ導入した、明示選択のPythonパッケージを対象にする。**
Pythonの実行環境、既存Action、builderと公開契約をそのまま利用できるためである。
外部拡張の導入経路が一つ成立することを先に示し、互換ホストの全機能は先行実装しない。

- 導入は利用者が管理する環境構築の操作とする。ホスト起動中に依存を取得・更新しない。
- 選択したパッケージのentry pointを読込み口とする案を採る。
  メタデータの列挙と検証は標準の `importlib.metadata` で行い、未選択のコードはimportしない。
- API世代は静的な登録宣言で識別し、対応しない世代はimport前に拒否する案とする。
  entry pointのgroup・識別方法・公開名は、段階P0で利用例とともに確定する。
- 選択が曖昧、重複、非対応、未導入の場合は起動を失敗させる。
  同名の別候補や別方式へ黙ってfallbackしない。
- importと稼働製品の生成は、利用者による明示選択の後に行う。
  Pythonのimportは任意コードの実行を伴う。メタデータの確認を安全な実行の保証にしない。
- 操作の生成能力を既存builder表へ適合し、稼働と同じ所有元を保持する。
  選択した拡張の未開始の稼働を受け取った時点で、終了の責任を登録する。

これはパッケージの自動導入・市場探索・実行中の更新ではない。
未選択のコードを実行しないことと、選択済みコードの安全性は別の保証である。

### 先に採用しない方式

| 方式 | 初回に採用しない理由 |
| --- | --- |
| 任意ディレクトリを走査して自動import | 選択前のコード実行と名前衝突を増やす |
| 独自のプラグインZIPとインストーラー | 初回に必要な導入は既存のPython配布で満たせる |
| プロセス分離と独自IPC | 強制停止・隔離の要求を確定してから必要な境界を設計する |
| 既存Stream Dock形式を初回入口にする | 入力だけでなく設定画面・表示・登録通信の不足がある |
| 汎用DIコンテナ・万能Context | 今必要な能力と所有だけを明示的に接続できる |

既存形式の再利用要求を取り下げる判断ではない。
[実物の互換性調査](../compatibility/streamdock.md)を後続設計の入力として維持する。

## 3. APIとして公開する範囲

### 維持する公開面

`Slot`、`Action`、`Result`、`Binding`と既存の能力viewを再利用する。
Slotへ外部拡張の識別子やpayloadを追加せず、操作の実行へ物理番号やSlotを渡さない。
C++ coreと機器SDKへ、拡張のimport・登録・開始・終了を追加しない。

### 追加候補と公開前の条件

このホスト案の追加候補は[基本設計の二つの境界](../design/extensions.md#最小の協調と契約提案)に限る。
公開する名前、Pythonでの署名、例外と所有の説明は、P0の利用側テストから決める。
この計画に実装済みのような署名例や仮のクラス階層は載せない。

- 拡張作者が参照するものと、ホストだけが使う読込み処理を分ける。
- 必須能力と明示的な継承を用い、不足した実装や不正な生成結果を開始前に拒否する。
  Python側の検査をC++コンパイラによる署名保証とは説明しない。
- 稼働の開始・終了はホストが呼ぶ。ActionへホストやBindingの所有を戻さない。
- 操作名の衝突は登録境界で拒否する。拡張の名前空間と既存launchを上書きしない規則を決める。
- 初回は一つのAPI世代だけを受け入れる。公開前に異なる世代を暗黙変換するshimを追加しない。
- 公開後の非互換変更は、対応世代・利用側の移行手順と一緒に扱う。
  内部native型のABIや外部製品の互換性を、Python APIの世代と混同しない。

新しい別配布SDKやAPIサーバーは、現段階では必要としない。
初回のPython拡張はビルド済みOpenDeckの公開契約へ依存し、C++コンパイラや機器SDKへ直接依存しない。
基盤をソースから構築する環境要件は[現行手順](../../README.md#セットアップ)に従う。

## 4. 設定と所有の接続

### 初回の設定

- 拡張の選択は、既存の操作設定とは別のホスト起動入力として追加する案とする。
- 既存JSONの必須項目は維持する。拡張選択用の項目を既存parseへ無条件に追加しない。
- 操作の設定は現在のactionsとbuilderの入口を使う。
  拡張全体の新しい設定形式や保存機構は、実際のユースケースが必要とするまで追加しない。
- 異なる操作定義と、同じ定義の共有は[所有境界](../design/extensions.md#初回の所有失敗境界提案)に従う。
  操作を別設定で使うテストと、同じ定義を共有する既存テストを両方維持する。
- 現行parseはActionを構成する。ホストがそれを純粋検証と誤認しない。
  純粋な宣言の検証、外部コードの読込み、builderによる構成、稼働開始を区別する。

### ライフサイクルの接続

[契約だけで追跡した開始・終了順](../design/extensions.md#contract-only-walkthrough)を使う。
入力元を構成・開始する前から、読み込んだ稼働の終了責任を所有する。
現在の `_execute` のfinallyへ処理を追加するだけでは、parseやFactoryでの失敗を回収できない。
接続単位の後始末は[現行CLIの扱い](../implementation.md#cliの結果表示)を参照する。
その回帰が通ることを、未実装の拡張稼働の解放やT11・T14全体の完了とは扱わない。

ホストが所有する範囲を囲み、Python標準のcontext管理など既存手段で逆順に解放する。
単なるExitStack任せで原因が失われないかを検証し、元の失敗と複数の解放失敗を残す。
通知登録を試みる前から解除を所有し、登録途中や入力接続の失敗でも解除する。
[現行Source](../../native/private/opendeck/source.hpp)は登録後の即時通知で失敗し得る一方、
未登録のremoveも安全に行える。この性質を初回に利用するSubjectの回帰条件とする。

停止と入力一件の引渡しの順序は[基本設計](../design/extensions.md#停止の順序と通知登録提案)に従う。
既存drainは空になるまで処理するため、そのままでは停止境界を設けられない。
ホスト側に一件単位の配送を置き、既存の選択・実行・結果報告の契約を使う案とする。
既存公開drainの振る舞いを黙って変更しない。

Ctrl+Cを協調停止へ適合する具体手段はP0で確定し、実装時は割込み経路も検証する。
任意のKeyboardInterruptを正常終了へ変える現行CLIの経路を、そのまま流用しない。
初回の正常終了は、実行中の同期呼出しが戻ることを前提とする。
ホストが持つBinding・Action・生成処理の参照は、稼働を終了する前に配送から切り離す。
Pythonモジュールの強制unloadや、任意の外部参照の消滅は約束しない。

## 5. 失敗時の運用と制約

| 事象 | 初回の推奨動作 |
| --- | --- |
| 選択・登録・設定・開始の失敗 | 入力配送を始めず、取得済みの所有物を解放して失敗を返す |
| Actionが失敗・結果不明を返す | 結果を記録し、既存どおり次の入力を処理する |
| Actionの例外・入力取得の失敗 | セッション全体を停止し、原因を残して後始末する |
| 終了時にも失敗する | 残りの解放を試み、元の失敗と区別して残す |
| 同期呼出しが戻らない | 停滞し得る。強制停止・他拡張の継続を保証しない |
| 再開 | 利用者が新しい稼働として開始する。自動retryやhot reloadは追加しない |

失敗を成功や未割り当てへ変換せず、欠けた能力を別の入力で代用しない。
診断には拡張と失敗段階を付けるが、設定値や秘密を丸ごと出力しない。
操作結果のstdoutと運用診断のstderrを分け、既存のCLI出力を壊さない。
初回の拡張作者の条件として、import・構成・開始・実行・終了でstdoutへ書き込まない。
診断はPython標準logging等でstderrへ出す。外部コードのstdoutを強制隔離する保証ではない。
この条件は拡張由来の出力に適用する。
[現行SDK由来の出力制約](../implementation.md#cliの結果表示)まで解消したとは扱わず、
live利用時のstdout全体がJSONのみになることは保証しない。

信頼済みの同一プロセス実行はsandboxではない。
拡張がプロセスを終了させる、importで資源を残す、GILを保持して停滞する等の影響は隔離できない。
初回の受入を、任意の第三者拡張を安全に運用できる証明として扱わない。
非協調的な停止や他拡張への影響の制限が初回から必要なら、P0でこの方式を再検討する。

## 6. 実装順序とTDDのテストリスト

各段階で一つの観察可能な振る舞いを選び、Redを実行してから最小のGreenへ進む。
テスト名・実行コマンド・意図した失敗を記録し、関連回帰を通してから責務と重複を整理する。
下記は未実行のリストであり、段階内の全テストを先に一括実装する指示ではない。

### P0: 利用例と境界の合意

初回ユースケース、同一プロセスの信頼条件と停滞制約を確認する。
拡張を選ぶ入力、API世代の静的宣言、公開名と必要な操作を利用側から決める。
停止要求と入力の引渡しの順序、Ctrl+Cの適合と異常な割込みの扱いもここで確定する。
一つのパッケージから複数の操作を提供し、別々のSlotへ割り当てる利用例を使う。
回転入力もホストへ接続する場合は、基盤側で定めた入力契約を利用する。操作固有のON/OFF契約は追加しない。
未承認の動作をテストの期待値で既成事実にしない。

受入: 外部拡張の作者と利用者の手順を、実装の内部状態なしに説明できる。

### P1: 最小契約と稼働の所有

- T1: 一つのパッケージの異なる操作を別々のSlotへ割り当て、選んだ操作だけを実行する。
  同じ種類の独立した操作定義は設定・状態を分け、同じ定義を共有する既存の意味は維持する。
- T2: 構成だけでは操作・資源取得をせず、開始後に初めて実行できる。
- T3: 設定失敗や未開始でも、取得済みの稼働を終了する。
- T4: 二つ目の開始が失敗しても、失敗途中を含む全取得済みの稼働を逆順に後始末する。
- T5: 必須能力の不足や不正な提供製品を、入力元の開始前に拒否する。

受入: 公開契約に従うfakeだけで正常系と部分失敗を確認できる。
T1の既存部分が初回からGreenなら回帰確認と記録し、新規Redとは数えない。

### P2: 選択した外部パッケージの読込み

- T6: 選択した提供元だけを読み込み、未選択のパッケージのコードを実行しない。
- T7: 未導入、曖昧な識別、非対応API世代を、import前に拒否する。
- T8: 一つの提供元の複数操作を登録でき、提供元の稼働を操作数だけ開始しない。
  提供元内・提供元間の操作名の重複と、予約済み操作との衝突で黙って上書きしない。
- T9: import・提供製品の生成が失敗したら配送せず、先に読み込んだ稼働を終了する。

受入: テスト用の別パッケージを同じ環境に導入し、明示選択から既存Actionへ接続できる。
標準ライブラリで満たせる範囲では新しいローダー依存を追加しない。

### P3: 標準起動経路からの一巡

- T10: CLIを編集せず、一つの外部パッケージの複数操作を別々のSlotからreplayで実行する。
  全段階の診断後もstdoutが結果形式で読める。
- T11: 通知を登録してからaddが失敗しても解除する。Factory・open失敗でも稼働を終了する。
- T12: 実行中Actionと次の入力がある状態で停止を要求し、戻った後は次の入力を取得しない。
  すでに取得済みの一件は実行責任を完了し、終了後の通知では再実行しない。
- T13: Actionの返す失敗・結果不明は継続し、例外・InputErrorでは停止する。
- T14: 元の失敗と複数の終了失敗を残す。add・remove失敗でも他の解放を飛ばさない。
  開始・実行・解放中の実際の割込みも通常停止と区別し、失敗と後始末の結果を保持する。
- T15: 拡張を選ばない既存CLI、JSON、launchとreplayの動作・出力が変わらない。

受入: 開始前から終了までの所有範囲を実経路で検証し、出力で失敗段階を区別できる。
停止の競合は同期点を持つfakeで確認し、sleep任せの成否判定にしない。

### P4: 公開・配布・検証範囲の記録

拡張用の独立パッケージ例、必要な公開API、設定、制約と対応API世代を説明する。
その例自身は機器SDK・内部native型・ホストのprivate実装をimportしない。

- T16: ビルド済みOpenDeckと別拡張のwheelをcheckout外の環境から利用できる。
- T17: Windows・macOS・Linuxで読込み・実行・終了を確認する。
- T18: fake・replayの成功と、N4 Pro実機で確認した範囲を区別して記録する。

受入: 対応を宣言する環境の実行証拠と、残る未確認範囲が公開ガイドにある。
既存のPyrightエラーや実機記録を、今回追加した問題・検証結果と混同しない。

## 7. 後続ユースケースへのゲート

このホスト案の初回がGreenになってから、ホストに必要な最小の契約差分を設計する。
基盤の押下・回転APIの検討は、このゲートから独立して進める。
以下は実装済み機能でも、次の段階の公開API案でもない。

### 基盤の入力APIとの接続

割り当て条件は[要件](../requirements/extensions.md#パッケージと機能の割り当て)、
責務は[基本設計](../design/extensions.md#複数機能の提供と割り当ての適合)を正本とする。
基盤側の未実装範囲と検証条件は[入力APIの対応計画](input-api.md)を参照する。
押下・回転への割り当てで、対象のON/OFF指定や照会を必須にするゲートは設けない。

基盤の契約を利用するホストとしての未実行のTDDリスト:

- T19: 押下と回転へ別々の操作実装を接続でき、一つのノブ用クラスを要求しない。
- T20: 選んだ操作の接続に必要な入力能力の不足を拒否し、構成時に操作や対象状態の取得を行わない。
- T21: 呼び出し側が実装内部を知らずに操作を呼び、失敗・結果不明を成功に置き換えない。
- T22: 操作の実装へキー入力監視や機器SDKへの依存を要求せず、基盤の提供データと契約で接続できる。

受入: 複数機能を持つパッケージでも、操作ごとの適合と非対応の理由を説明できる。
要求の確認、最小契約の設計、Red・Green・Refactorの順に進め、単発操作の回帰を維持する。

### 継続入力を複数拡張で使う

- 同じButtonの履歴はホスト側の一か所で取り出し、不変の記録を配送する。
- 同じ消費型Inputを各拡張に渡さず、欠落・重複・順序・終了後の配送を検証する。
- 失敗する配送先と停滞する配送先を分け、影響範囲・容量・未配送分・再開を決める。
- 現在状態と履歴、入力元の利用不能を混同しない。
- 単発入力のmakeとButtonのmake_buttonsを併用する条件は、取得経路の所有から検討する。
  一つの機器へ別々に接続すればよいとは仮定しない。

受入: 同じ入力を二つの拡張が奪い合わず利用でき、切断・終了・停滞時の結果も説明できる。
長押しの解釈や共通閾値はホストへ追加しない。

### 既存形式の互換実行

[互換性調査の検証候補](../compatibility/streamdock.md#次の検証候補)へ戻り、
対象拡張の起動・登録・配置・設定・表示に必要な差分だけを設計する。
外部のcontextやWebSocket形式をSlot・Actionへ押し込まない。
Windowsの実行物をmacOSでも動作可能と表示せず、部分対応を全体互換へ広げない。
破壊的な操作やサービス変更は、登録・設定の検証と分けて承認する。

## 8. 実装前に残す判断

| 判断 | 必要になる段階 |
| --- | --- |
| 単発操作を先行する順序と、同一プロセス実行を許容するか | P0 |
| 明示選択の入力、API世代宣言、名前空間と公開名 | P0からP2へ進む前 |
| 回転入力をホストへ接続する範囲 | 基盤の入力契約を定めた後のホスト接続設計。基盤のAPI設計を待たせない |
| 拡張全体の設定・保存・更新が必要となる具体例 | そのユースケースの設計前 |
| 停止と入力の引渡し、Ctrl+Cと異常割込みの区別 | P0 |
| 強制停止・他拡張の継続が必要な運用条件 | P0、および継続入力の設計前 |
| 最初に互換性を実機検証する対象と必要能力 | 互換実行の詳細設計前 |

## 9. 設計レビューで反映したこと

独立した反証レビューの指摘を、現行の契約・実装と照合した。

- Sourceは登録を変更してから通知するため、addの試行前から解除責任を持つ順序にした。
- 空まで処理するdrainの再利用だけでは停止できないため、配送単位と停止の順序を定めた。
  Ctrl+Cの具体的な適合と割込みの扱いは、P0で確定する判断として明記した。
- 同一プロセスのstdoutは隔離されないため、拡張作者の出力条件と外部パッケージの検証を追加した。

残る主な前提は、信頼済みコードの協調、稼働製品の生成で資源を取得しないこと、
同一環境へ導入した配布物の静的宣言で対応を判定できることである。
これらは承認や実行検証が済んだことを意味しない。

## 10. 検証方針と今回の範囲

実装段階では[AGENTS.md](../../AGENTS.md#確認コマンド)の固定ツールと標準コマンドを使う。
公開契約・ホスト・外部読込み・CLIの狭いテストから始め、pytest、lint、配布物の検証へ進む。
C++やbindingを変更する必要が出た場合だけ、その契約とnativeの回帰も追加する。

このプランの作成時には、正本文書との整合、ローカルリンク、Markdown診断と最終差分を確認した。
後続のCLIの回帰確認と、未実装の拡張ホストの動作確認は区別する。
この計画の記載を、拡張ホストの実装テストや実機検証の成功とは扱わない。
