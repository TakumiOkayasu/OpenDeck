# 入力APIの対応計画

2026-11-11に、main `880256f` の文書・コード・テストを利用者の設計方針と照合した。
この文書は調査結果と次の設計・検証手順を管理する。新しい公開APIを実装済みとは扱わない。
要求の正本は[全体要件](../requirements.md)、[ボタン入力](../requirements/buttons.md)、
[回転入力](../requirements/rotation.md)、責務と依存方向は[基本設計](../design.md)とする。

## 現行実装との照合

| 対象 | 現在の実装・記述 | 判断と対応 |
| --- | --- | --- |
| [C++のAction](../../native/include/opendeck/contracts.hpp)と[PythonのAction](../../src/opendeck/ports.py) | 引数なしのrunを必須とし、実装側が具体処理を提供する | 単発操作の契約として再利用する |
| [配送](../../native/src/runtime.cpp) | Bindingで選んだActionのrunを呼ぶ | 実装内部を知らない呼出しは方針と一致する |
| Button | 押下状態・変化・通知の能力を合成する | 入力側の能力として維持し、操作対象のON/OFF状態と混同しない |
| [設定とBindingの構成](../../src/opendeck/config.py) | 操作定義ごとにActionを作り、同じ定義は複数Slotで共有する | 別定義の独立と同じ定義の共有を維持する |
| [SDKアダプタ](../../src/opendeck/adapters/streamdock.py) | BUTTON以外の回転などを操作入力として受け付けない | 回転の契約・データ・接続は未実装。ログ取得を対応済みの根拠にしない |
| 拡張利用の旧要件 | トグルへの割り当てにON/OFF能力を要求する | 押下・回転への割り当て条件から削除し、対象の状態操作は実装側へ戻す |
| 拡張ホストの案 | 導入・稼働管理と後続能力のゲートを提案する | 基盤の入力APIから独立した利用側の案と位置付ける |

[既存の拡張テスト](../../tests/test_extensions.py)と[公開APIテスト](../../tests/test_api.py)には、
Actionの差替え、設定・配送、SDKへの非依存を確認するものがある。
これらのテストの存在を、未実装の回転や押しながら回転の検証成功とは扱わない。

## 設計から実装へ進める順序

1. 利用側の例として、単発押下・通常回転・押しながら回転へ独立した操作を割り当てる流れを記述する。
   操作の中身はfakeにし、具体的な拡張機能やON/OFF仕様を基盤へ取り込まない。
2. 必要な回転データの型・意味・単位と、操作へ渡す最小の契約候補を比較する。
   既存のRead・Input・Subjectの再利用を検討し、ButtonとActionへ一律に能力を追加しない。
3. 値を伴う操作の構成と割り当ての接続を定める。
   現行のSlotとBindingは値を伴わない単発経路なので、そのままで回転にも対応できるとは仮定しない。
4. 契約候補と利用例を確認してから、基本設計・詳細設計へ反映する。
   押下中の回転の判定、同期、内部状態や単発押下の抑止は、その振る舞いを実現する実装へ閉じる。
5. 一つの利用側テストからRed・Green・Refactorを進め、公開契約、機器からの適合、組み立てを接続する。
   抽象データを提供する側と操作を実行する側を、機器固有の分岐で結ばない。

基盤の契約設計は、[ホストの実装計画](extension-host.md)と独立して進める。

## 未実行のTDDリスト

- 単発操作の実装が、キー入力監視・機器SDK・物理識別子を使わず呼び出される。
- 呼び出し側が具象型に分岐せず、同じ契約の別実装へ差し替えられる。
- 回転データが、定めた型と意味で利用側へ届く。
- 押下と回転へ異なる操作を割り当てられ、ノブ全体を担う一つの実装を要求しない。
- 押しながら回転する利用例を、個別の処理内容を共通APIへ追加せず接続できる。
- 契約に必要なメソッドが不足した実装や、接続に必要な能力が不足する組み合わせを拒否する。
- 入力の利用不能と入力なしを区別し、別の割り当てへデータや状態を取り違えない。
- 既存のAction・Button・Bindingと設定・単発配送の回帰を維持する。

既存条件が初めからGreenなら回帰確認として記録し、新規Redと数えない。
公開契約のテストで、全能力を一つのクラスへ集めることや、押下・回転を横断する新しい順序保証を要求しない。
判定アルゴリズムや同期の確認は、それを所有する実装のテストで行う。

## 公開前に残す判断

| 判断 | 確定する内容 |
| --- | --- |
| 回転データ | 必要な方向・量、単位、機器から独立した意味 |
| 操作への受渡し | 既存契約の再利用範囲と、値を受ける操作に必要な最小の契約 |
| 割り当て | 独立した操作を選択・構成・接続する方法と、設定で表現する範囲 |
| 対応能力 | 機器・適合実装が提供できる範囲と、不足を報告する方法 |

これらは未確定であり、この文書だけで署名や設定形式を固定しない。
対象のON/OFF指定・反転・照会・同期は個別操作側の仕様とする。
