# 入力から操作実行までの基本設計

通常の物理ボタンの押下から、割り当てた操作を実行できるようにする。[全体要件](requirements.md)の共通要件を前提に、入力の受信から操作の実行までを基本設計として定める。

Windowsでの利用を先行し、macOSでは機器・OSとの接続実装を交換できる構成にする。基本設計は言語に依存しない契約を定め、今回の言語・取得方式・認識方式は[詳細設計と実装](implementation.md)で管理する。

## 到達点と範囲

接続可能な機器から理想入力を成立させ、上位のキーコンフィグに従って操作を実行する。単独操作と同時押しの取得・認識方式は詳細設計で定める。初期範囲では動作開始前に割り当てを構成し、実行中の変更は扱わない。

入力の実現、入力への割り当て、操作の実行を別の責務にする。操作内容は入力方法から独立させ、個別機能を機器側の分岐に組み込まない。

この到達点では、通常ボタンの単独・同時押し、操作との対応付け、実行、未割り当てと失敗の識別を扱う。設定画面、保存形式、機器への描画、長押し、ノブ、タッチ、動的な割り当て切替は、それぞれの検討で定める。

拡張がボタンの開始・継続・終了を必要とする場合は、[ボタン能力の基本設計](design/buttons.md)の別契約を使う。
この文書の単発入力へ保持状態を混在させず、短押し・長押しなどの解釈を基盤へ追加しない。

## レイヤーと依存

上位は、必要とする理想的な能力と意味を定義する。下位は、SDKやOS、機器の制約を引き受けてその契約を実現する。理想的な契約を利用する層と、OSイベントや機器からの入力を直接受け取る層との間には、必要なだけ中間層を置ける。層数の上限や固定数は設けない。中間層も上位に対しては契約を実現し、下位に対しては必要な契約を利用する。各境界が何を隠すかと各層の責務を明確にし、一つのアダプタに取得・解釈・割り当て・実行を集約しない。

| 責務の位置 | 仕事 | 知る必要がある情報 |
| --- | --- | --- |
| 上位の入力定義・キーコンフィグ | 理想入力と、操作への対応関係を定める | 機器から独立した入力の意味、操作・対象・設定値 |
| 割り当ての適用 | 成立した理想入力から、実行する操作を確定する | 理想入力、一貫した割り当て、操作の契約 |
| 理想入力の実現 | 現実の入力を、宣言された理想入力へ適合させる | 理想入力の契約と、それを実現するための下位情報 |
| 外部との接続 | 機器やSDKから取得し、OSや機器へ反映する | 外部API、接続条件、外部の形式 |
| 操作の実行 | 操作の規則に従い、対象へ働きかける | 操作の意味、必要な引数、対象の抽象契約、実行結果 |

表は責務の位置関係を示すものであり、各行を一つの層やクラスに固定するものではない。入力経路と対象・表示への経路は分かれ、途中の抽象化も必要なだけ重ねる。物理動作を扱う部分の直上には、その動作を知らずに利用できる契約を置く。

各境界の契約は、それを必要とする上位側が定義し、下位側が実装する。キーコンフィグは理想入力の契約を使い、操作実行はActionと対象の抽象契約を使う。上位からSDKやOS固有の実装を参照しない。

実行時の処理の流れと、コードの依存方向は別である。入力の成立から割り当ての適用、操作実行、対象への反映と進んでも、依存は上位が定義した契約へ向ける。純粋な規則を独立した最上位の層へ一括配置することもせず、その規則が属する責務に置く。

### 組み立て

組み立ては各層の外で行う。Factoryで外部と接続する製品群を作り、上位の入力定義、現実との適合設定、キーコンフィグ、操作と対象の実装を接続する。組み立て側は関係を構成する責務を持ち、入力認識や割り当ての選択規則を実行時に肩代わりしない。

### 操作の追加と構成

組み立て側は、利用する操作の種別と、その設定から構成済みActionを返す生成処理を明示的に対応付ける。共通の設定処理は、この対応を使って生成を依頼し、個別操作の設定項目や対象の具体実装を知らない。操作を追加しても、共通の設定処理、理想入力の実現、Bindingの選択、Actionの実行手順を変更しない。

各生成処理は、その操作に固有の設定を検証し、必要な引数と対象の参照を確定する。対象の抽象能力は組み立て側から必要なものだけを渡し、機器用Factoryへ操作の生成を集めない。構成時に操作を実行したり、対象の現在状態を読み書きしたりしない。生成時の設定不備と、runによる実行結果は別に扱う。

## 理想入力とキーコンフィグ

アプリケーションや拡張機能に提供する仮想キーを、理想入力のSlotとして定義する。
Slotは上位の入力定義が宣言する仮想的な入力点である。
契約と入力定義は上位が所有し、下位の実現側が現実の入力から成立させる。
識別と成立の意味は機器から独立させ、機器を交換してもSlotと操作の割り当てを維持できるものとする。
今回の入力は「指定したSlotが一回成立した」という合図であり、物理ボタン番号、押下・解放、座標、回転量を表さない。

現実の入力をSlotへ対応付ける適合設定と、Slotを操作へ対応付けるキーコンフィグを分ける。前者は機器側の情報を扱う下位の責務、後者は上位の責務とする。SDKの識別子を別名へ置き換えるだけでは理想入力への適合としない。
同じSlotへ割り当てる操作を変更するために、物理入力との適合を変更しない。
逆に、入力手段の交換に伴う適合変更で、Slotや操作への割り当てを変更しない。

同時押しについては、設定側が複数のSlotによる成立条件と、その条件に対応するSlotを定義する。実際の成立を検出する責務は、理想入力の実現側に置く。そこへ渡すのは入力の条件であり、実行する操作、対象、操作の引数ではない。実現側は必要な非公開状態を使って判定でき、公開された単発の合図から同時性を再構成する必要はない。

入力の定義、割り当ての設定、実行時の割り当て適用は別の仕事とする。今回の実行時割り当ては、Slotと構成済みActionの対応関係を持つ不変のBindingとする。設定画面と保存形式はこの基本設計の範囲外だが、その実装を機器用アダプタへ持ち込まない。

値を伴う入力を追加する場合は、上位が必要な型と意味を定める。外部値を理想入力の値へ適合させる処理と、理想入力の値を操作の引数へ変換する処理を分ける。共通の数値やパーセンテージへ一律に押し込めない。今回のSlotの発生には値を付加しない。

入力を定義できることと、ある機器でその入力を実現できることは分ける。下位が契約を満たせない場合は適合不可として報告し、設定を勝手に書き換えたり、対応済みとして扱ったりしない。

表示内容の形成と、表示先への適合・描画も別の経路として分ける。Viewは渡された内容を描画する。設定画面で実機の配置を見せる場合も、表示用の情報とキーコンフィグの意味を混ぜない。

## 責務と契約

必要な振る舞いと制約から責務を分け、抽象契約と整合条件を定めてから具体化する。SDKのAPIや既存のクラス構造を、そのまま上位の契約にはしない。

各クラス・メソッドは一つの責務を持つ。独立した能力は小さな契約に分けて合成し、利用側には必要な能力だけを渡す。能力の分割と、実装オブジェクトを分割する判断は別に行う。同じ状態を共有する必要がある能力は、整合条件を保った一つの実装として提供できる。

名前は文脈内の役割を短く表す。単複の差だけで異なる責務を区別せず、長い説明を名前に詰め込まない。短い名前で役割を説明できなければ、命名前に責務と境界を見直す。

契約名は言語に依存しない役割名とし、実装での表現は[詳細設計と実装](implementation.md)で定める。交換する境界を契約にし、計算や内部の協調処理まで一律にインターフェース化しない。

| 契約 | 操作 | 責務 |
| --- | --- | --- |
| `Input<T>` | `take` | 未処理の入力を一回分取り出す |
| `Subject` | `add` / `remove` | Observerとの対応を管理する |
| `Observer` | `on_change` | 通知を受ける |
| `Action` | `run` | 構成済みの操作を実行する |
| `Link` | `open` / `close` | 接続の開始と解放 |
| `Factory` | `make` | 外部との接続に必要な関連製品を生成する |

Linkは外部との接続実装と組み立て側の契約とする。開始結果は接続と必要な初期化の成否を区別できるものとし、機器が見つかったことだけで入力を受理できる状態とは判断しない。キーコンフィグと操作実行は接続や初期化を扱わない。

`Input<T>`は入力の取得と消費を含む能力とする。今回の理想入力境界では`Input<Slot>`として提供し、takeは次に成立したSlotか空を返して、その発生に対応する未処理項目を取り除く。同じSlotが繰り返し返されても、それぞれ別の発生である。Slotオブジェクト自体を消費するわけではない。物理入力の情報は返さない。

on_changeは値を渡さず、未処理の理想入力があることを知らせる。割り当てを適用する処理がtakeで入力を取り出す。通知の回数を入力や実行の回数と対応させず、最後の状態を読む方式にも置き換えない。`Input<Action>`は割り当て適用後の要求を配送する場合には使えるが、機器側の固定契約とはせず、今回そのための待ち行列は追加しない。

ActionはCommandパターンの実行単位とする。割り当ての適用によって、操作の意味、必要な引数、対象の参照を確定してから実行側へ渡す。runには入力方法やSlotの情報を渡さない。引数の型と意味は操作側が定め、座標や回転量を汎用数値へ包み直すだけの抽象化はしない。

操作の実行側は、その要求が物理入力、画面操作、その他の呼び出しのどれから来たかを知らずに実行できる。実行の完了、失敗、結果不明を区別し、対象の値や状態をこの共通契約に混ぜない。完了の意味は個別操作の仕様に従う。

今回の固定Actionは繰り返しrunでき、実行結果は各呼び出しに属する。要求の構成時には対象の状態を読み書きせず、現在状態が必要な操作は実行時にその状態を取得する。

Inputは契約に従った入力の取得、Actionは入力元に依存しない実行能力、Linkは接続を表す。SubjectとObserverはObserverパターンの役割名を使う。Slotは理想入力の位置、Bindingは入力と操作の対応関係を表す。Bindingを持つのは上位の割り当て側であり、機器側は操作への割り当てを参照しない。

### 生成と所有

Abstract Factoryを採用する。Factoryは機器の記述、実現する理想入力の定義、現実との適合設定を受け、関連するLink、`Input<Slot>`、Subjectの未接続の製品組を生成する。関連製品は同じ接続と入力の実現を共有し、入力取得と通知は同じ未処理入力を参照する。接続を開始するのはLink.openであり、makeでは開始しない。

組み立て側は構成済みActionを上位のBindingへ渡し、機器用Factoryには渡さない。入力に応じて引数が変わる機能を追加する場合も、理想入力から操作の型と意味への変換、操作要求の構成を割り当て側で行う。機器用Factoryへ個別操作の実装を集めず、選択規則や操作からFactoryを呼ばない。

Sourceは理想入力の保持と配送を担い、`Input<Slot>`とSubjectを別の能力として提供する。入力認識や操作選択までSourceの責務へ集約しない。物理イベント、保持状態、接続の識別情報は公開しない。入力を取り出す処理側は一つとし、複数のObserverで同じ項目を奪い合わない。

## 純粋関数と副作用

純粋関数は、同じ引数から同じ結果を返し、外部から観測できる副作用を起こさない関数とする。結果は明示的な引数に依存し、処理中に外部の可変状態や現在時刻を取得・変更しない。

読み取り専用の参照でも、参照先の現在状態が外部で変わるなら純粋性は保証されない。計算に必要な取得済みの不変の値を引数として渡し、状態の取得は計算の外で行う。

生成という行為やFactoryという役割名だけで純粋性を判断しない。引数だけから値を構成する計算と、外部への接続・取得・状態変更を伴う生成処理を分離する。

### 純粋関数の配置

純粋性と所属する層は別の判断とする。物理入力を解釈する計算は、純粋にできても入力アダプタ内に置く。基本設計では計算と副作用の分離を定め、内部データの型、状態遷移、関数の具体的な構成は詳細設計で定める。

| 処理 | 純粋にする部分 | 副作用を持つ部分 |
| --- | --- | --- |
| 理想入力の実現 | 取得済み情報、入力定義、必要な文脈から成立を判定する計算 | 外部からの取得、認識状態の保持、成立した入力の配送 |
| 割り当ての適用 | 理想入力とBindingから操作を選ぶ計算。値を伴う場合は操作の引数への変換 | 入力の消費と、構成された操作を実行側へ渡す処理 |
| 操作の実行 | 操作に必要な値の検証と計算 | 必要な状態の取得と対象への反映 |
| 表示 | 取得済み情報から表示内容を形成する計算 | Viewによる描画 |

純粋な計算が使う情報は引数で渡す。実行する操作の参照を返す選択処理も、操作を実行・照会せず、その内部状態に依存しなければ純粋にできる。

入力の実現側が理想入力を確定し、割り当て側が純粋な選択規則によってActionを決め、実行側がrunを呼ぶ。必要な状態の取得と反映は、操作側の契約を実装した対象側が担当する。各責務で計算と副作用を分け、純粋であることを理由に下位固有の知識を上位へ移さない。

## 基本設計と詳細設計の境界

| 基本設計で定めること | 詳細設計で定めること |
| --- | --- |
| 上位が理想入力と操作への割り当てを定め、下位が理想入力を実現する | SDKや機器へ適合させる内部の分割と具体的な実装 |
| 入力の成立、割り当ての適用、操作実行を分ける | callback、イベント通知、ポーリングなどの取得方式 |
| 単独・組合せを理想入力として扱い、同じActionへ対応付けられる | 認識の状態遷移、候補の判定、確定時点、必要な待機 |
| 上位は物理情報を解釈しない | SDKの実在するAPI、入力識別子、内部データの表現 |
| 成立した入力を順序どおり引き渡す | 蓄積方法、起床処理、同期方法、取得方式に応じた制約 |
| 取得・保持・通知と計算を分離する | SDKや実行環境に適合する具体的な関数・処理構成 |

割り当て適用の契機は理想入力の引き渡し、操作実行の契機は確定したActionの引き渡しとする。物理側でどのcallbackを使うか、状態を調べて変化を認識するか、いつ候補を確定するかは上位の契約に含めない。SDK側のcallback数、成立した入力数、操作の実行数はそれぞれ区別する。

### 利用者向け動作仕様の確認

同時押しで単独操作も実行してよいかは、利用者から観察できる入力の成立規則として確認する。規則の所有は上位、規則に従った検出は実現側とする。これはcallbackやポーリングを選ぶ実装判断とは分け、上位境界の抽象化を止める条件にはしない。

## 実行の流れ

1. 上位の入力定義とBindingを構成する。組み立て側がFactoryの関連製品、適合設定、割り当て側、操作と対象を接続し、入力を消費するObserverを登録する。初回の配送も予約する。

2. 外部との接続実装が接続と必要な初期化を完了する。入力の実現側が、理想入力の契約を満たせる状態で現実の入力を受理する。

3. 入力の実現側が単独・組合せの成立を検出し、対応するSlotの発生をSourceへ渡す。Sourceが未処理入力を保持し、on_changeで処理側へ通知する。

4. 割り当て側がtakeでSlotの発生を受け取り、BindingからActionを選ぶ。未割り当てなら、その入力を未割り当てとして識別し、操作の実行要求にしない。物理状態や接続の詳細は確認しない。

5. 実行側が選ばれたActionのrunを呼び、実行結果を受け取る。必要な状態取得、規則の適用、対象への反映は、その操作の契約に従う。

6. 実行の失敗と結果不明を識別し、自動再実行しない。入力の適合・取得に関する診断、未割り当て、操作の実行結果を区別する。

7. 未処理入力が空になるまで処理し、次の通知を待つ。各操作の実行契約が完了してから、次の入力に対応する操作を実行する。

SDKの受信処理で割り当ての適用や操作実行を進めない。外部からの取得と必要な入力処理を終えて戻り、成立した理想入力を上位へ引き渡す。同期・非同期の実装方式や途中の処理分割は、言語とSDKの詳細設計で定める。境界が増えるたびに待ち行列を追加することはしない。

## 整合性の規約

責務の分離とは別に、次の整合性を守る。

- 入力定義と操作への割り当ては上位が所有する。外部からの取得、現実との適合、非公開の認識状態は入力の実現側が管理し、操作を選ばずに理想入力を提出する。

- 成立した理想入力は確定した順に保持し、各項目を一度だけ引き渡す。通知がまとめられても項目は失わない。未処理入力を残したまま通知の取りこぼしで処理が停止しないことを配送契約とする。

- on_changeは入力の配送を予約するだけとする。Sourceの内部ロックを保持したまま外部Observerを呼ばない。状態の変更通知と、入力の到着通知は別の対象として扱う。

- 成立判定は一つの整合した入力定義に従い、操作選択は一つの整合したBindingに従う。操作の意図と必要な引数は実行側へ渡す前に確定し、実行側で物理入力やSlotから選び直さない。

- 切断・終了時は接続を無効にし、未確定の認識、未引き渡しの理想入力、非公開の保持状態を破棄する。古い受信から新しい入力を提出しない。takeによる引き渡しと切断は実現側で順序付ける。

- takeで引き渡すと、その入力の発生一回分の処理責任が割り当て側へ移る。対応するActionがある場合に一回の実行を要求する。SlotやActionオブジェクト自体の所有が移るわけではない。引き渡し済みの入力は入力元の切断だけでは取り消さず、選ばれた操作は自身の成否や取消規約に従う。

- 入力の適合・取得に関する診断、割り当て側の未割り当て、操作の実行結果は別に管理する。操作の失敗や結果不明に対して自動再実行しない。

この規約により、キーコンフィグは理想入力だけで割り当てを扱い、実行側は入力元を知らずに操作を実行できる。機器からの通知欠落や、外部操作の完了を無条件に保証するものではない。

## 抽象契約とSDKの適合

独自の抽象契約を正とし、SDKはそれを実現する外部依存としてアダプタ内で利用する。SDKの型、列挙値、callbackの個数、スレッド構成を、そのまま操作側の仕様にしない。SDKを交換・更新する場合も、適合するのはアダプタ側である。

公式のDevice SDKで機器へ直接接続する方針とする。機器の列挙、接続、初期化、物理入力と理想入力の対応、SDKの通知方式とスレッドは下位で扱う。操作への割り当ては上位で扱う。WindowsとmacOSで変わる取得・反映処理は対応するアダプタが実装し、理想入力、キーコンフィグ、操作の意味と契約を維持する。

アダプタの適合性は、理想入力を実現するための個別入力の識別、保持と解放の取得、通知の順序・重複、接続の開始・終了について確認する。同時押しに必要な情報を取得できない場合は、該当する理想入力を実現可能として扱わない。適合可否は下位で判定し、上位へは抽象契約上の結果を返す。SDK固有の制約をキーコンフィグや操作の規則にしない。

実在するSDKのAPI、固定したリビジョン、ソース上の根拠と実機で未検証の条件は[詳細設計と実装](implementation.md)に置く。

## 抽象化の完了条件

上位境界の抽象化は、入力の具体的な取得・認識方式を選定する前に、次の契約で判断する。

| 確認すること | 完了と判断する条件 |
| --- | --- |
| 層境界 | 各上位が必要な理想契約を定義し、下位の実装を知らずに利用できる。層数を固定しない |
| キーコンフィグ | 理想入力への操作割り当てを上位が所有し、機器・SDKの交換では現実との適合だけを交換できる |
| 操作要求 | 単独、同時押し、仮想操作から同じActionを構成でき、実行側に入力元の情報が不要である |
| 取得方式からの独立 | callbackやポーリングを交換しても、理想入力、割り当て、実行の契約が変わらない |
| 責務と整合性 | 入力の実現、割り当て適用、実行を分け、配送・未割り当て・失敗・切断の責任が明確である |
| SDKとの関係 | 独自契約を正として、SDKを下位で適合させられる |

本基本設計では、理想入力の実現、キーコンフィグの適用、操作実行の境界を定めた。具体化は各境界が隠す下位情報と、機器交換時に維持する上位の定義をこの条件で確認してから行う。取得・認識方式が未選定であること自体は、上位契約の成立を止める条件にはしない。

## 実装時の完了条件

| 確認すること | 成立条件 |
| --- | --- |
| Windows実機の操作 | 通常ボタンの単独と同時押しを理想入力へ適合し、Bindingに従ってActionを呼び出せる |
| 上位の独立性 | キーコンフィグはSDKや物理入力を参照せず、実行側は入力元や割り当てを参照しない |
| 機器・OSの差し替え | 適合する下位実装を交換しても、同じ理想入力とキーコンフィグを利用できる |
| 取得方式の差し替え | callbackやポーリングを変更しても、上位の処理を変更しない |
| 認識と動作仕様 | 詳細設計で選定した認識方式が、上位で定めた入力の成立規則を満たす |
| 入力の配送 | 成立した入力を規約に従って引き渡し、割り当て済みの各発生に対して一回のrunを行う |
| 未割り当てと失敗 | 適合不可・未割り当て・実行失敗を各責務で識別し、自動再実行しない |
| 切断と再接続 | 未確定の認識と未引き渡し入力を破棄し、古い受信から新しい入力を提出しない |
| 純粋関数 | 外部依存なしで計算部分を検証でき、所属層の責務を維持する |
| SDKとOSの適合 | 下位が独自契約を満たし、上位の定義と規則を変更しない |

## 詳細設計と実機で確定する事項

実装言語とSDKの利用形態、実在するAPI、callbackやポーリングなどの取得方式、入力認識の状態遷移と確定方法、内部データの型と表現を詳細設計で定める。待ち行列と起床処理の同期、実行結果と接続失敗の表現、蓄積の上限と受理できない場合の扱いも定める。

実機では通常ボタンの識別子、複数入力の保持と個別の解放、押下順と解放順、長押し中の通知、通知欠落・重複、切断・再接続時の状態を確認する。純正ソフトとの同時利用可否と初期化時の機器への影響も、接続条件として確認する。
